# VPS-MCP — Automatic private Docker installation (Phase 05 foundation)

**Scope:** Portable, private-first Compose service. No manual `.env` edits, exposed Docker daemon, public admin login, or VPS firewall changes.

## 1. Install on a fresh Ubuntu VPS

After installing Docker Engine + Docker Compose and cloning the repository, run:

```bash
bash scripts/install.sh
```

The installer generates `.env` with mode `0600`, a fresh random setup token and its SHA-256 hash, and brings up the non-root container using Compose. The **secret token is shown once in the terminal**, never stored in plaintext. The Docker-managed `vps-mcp_mcp-data` volume persists admin credentials, OAuth registrations, permissions, control settings and audit logs.

**First visit:** From your laptop, establish an SSH tunnel to the VPS:

```bash
ssh -L 3000:127.0.0.1:3000 ubuntu@YOUR_VPS_IP
```

Open `http://127.0.0.1:3000` locally. Complete the mandatory setup screen with the one-time token, your preferred admin username, and a new password (minimum 12 characters). The UI shows **admin** and the starter example **Pass@123** to make onboarding recognizable, but **Pass@123 is never a valid final password**. You must change it before login is possible. Then sign in with your new credentials.

**Why not allow the starter password?** It is public and predictable. Making it a usable remote administrator password would allow hostile users to seize new VPS installations. The one-time token is the required ownership proof.

## 2. Isolation model

- API container UID/GID 10001:10001; read-only filesystem, dropped Linux capabilities, no-new-privileges, memory/CPU/PID limits.
- Only `127.0.0.1:3000` is published on the host. No public inbound port is opened by the project.
- Named volume for private data, initialized once using a short-lived root `init-data` helper which only changes volume ownership.
- Docker socket, privileged management container, root shell, Git deployment automation and host filesystem mounts are **not present** in the default stack.
- `MCP_ENABLE_WRITES=false`, `MCP_ALLOWED_TOOLS=system_status,disk_usage` are generated by default. Existing advanced toggles cannot override these environment ceilings.
- OAuth registration is closed until an authenticated administrator opens enrollment. External ChatGPT cloud clients cannot connect to localhost; public HTTPS and live OAuth integration are separate release gates.

## 3. Operate without editing .env

```bash
bash scripts/status.sh
bash scripts/stop.sh
bash scripts/update.sh
bash scripts/uninstall.sh
```

Stop and uninstall retain the named volume and the generated `.env`; neither runs `docker compose down -v`. The installer never overwrites an existing `.env`. **Keep a secure backup of both** before VPS migration.

## 4. Security and release limits

- This is a **local/SSH-tunnel-only deployment profile**, not yet a publicly accessible ChatGPT MCP service.
- The optional Docker/Git broker remains un-packaged in the default Compose system because unrestricted Docker socket access is effectively root-equivalent and the existing shared-secret architecture is not independent approval authorization.
- Network TLS, public DNS, Caddy/reverse proxy/Cloudflare Tunnel, ChatGPT OAuth callback, broker isolation and end-to-end VPS testing are not claimed complete.
- A lost setup token cannot be regenerated from an anonymous HTTP request. Restore the original setup terminal record or use an explicitly authorized local recovery procedure.
- Container build still uses resolved package dependencies (`npm install`); a committed deterministic lockfile and `npm ci` are required before declaring a hardened reproducible release.
- Public production exposure should wait until authentication, DNS/TLS, backup/restore, broker threat model and live connection are verified on the target VPS.
